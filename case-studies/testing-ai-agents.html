How I test AI agents beyond the final answer

A chatbot can return a good-looking answer and still fail underneath. With AI agents, I want to know not only what the model said, but what it did: which tools it called, what state changed, what it remembered, and whether the task was really completed.

The problem with testing only the final response

Traditional UI testing often has a clear expected result. AI systems are different: the wording can change while the behavior is still correct.

But the opposite is also true. The final answer can sound correct even when the agent called the wrong tool, repeated an action, lost context or reported completion without actually changing the system state.

What I look at

  • Whether the correct tool or API was called
  • Whether the tool received the right parameters
  • Whether retries create duplicate actions
  • Whether state really changed after the agent says the task is complete
  • Whether memory and context survive multi-turn conversations correctly
  • Whether the model invents facts or actions that never happened
  • How the system behaves under prompt-injection attempts

Verified completion matters

One of the most important checks for an agent is simple: if it says “done”, can I independently verify that it is actually done?

I do not treat the model's final sentence as the source of truth. The system state, API result or tool output should confirm completion.

Retries and duplicate actions

Retry logic is useful, but it can also create a different class of bugs. If an agent retries an operation that already succeeded, it may create duplicate records, duplicate messages or repeated external actions.

So I test both successful retry behavior and what happens when the system is uncertain whether the previous action completed.

Memory and multi-turn behavior

AI systems often need to remember information from earlier turns. I test whether the right context is retained, whether old context incorrectly leaks into a new task, and how the system behaves when the conversation becomes long or contradictory.

Prompt injection and guardrails

I also test whether user content can push the agent outside its intended behavior, override instructions or influence tool use in unsafe ways.

The goal is not to invent exotic attacks for their own sake. It is to understand where untrusted input meets real actions.

My practical approach

I treat AI testing as a combination of classic QA and evaluation. I still care about APIs, logs, state, reproducibility and business rules. The new part is that the exact output can vary, so the test needs to focus more on behavior and evidence.
